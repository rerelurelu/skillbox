# 実装計画レビュー基準

レビュー範囲が実装計画・タスクリスト・他のエージェントが実行する手順書のときに使う。

指摘には行番号ではなく、対象ステップの番号か見出しを添える。

## 観点

- **手順の抜け漏れ**: 各ステップの成果物が、次のステップの前提を満たしているか。前提を満たさないまま次に進むステップはどれか
- **依存関係の矛盾**: 後のステップの成果物を前のステップが必要としている箇所がないか。並列実行できると書かれたステップが同じファイル・同じリソースを触っていないか
- **ロールバック可否**: マイグレーション・破壊的なデータ更新・削除・外部への送信・デプロイなど、元に戻せない操作を含むステップに、失敗したとき元の状態に戻す手順が書かれているか。通常のコード編集ステップにまでロールバック手順を要求しない
- **検証ステップの有無**: 各フェーズの完了を、実行して確かめる手段（テスト、コマンド、確認画面）が書かれているか。「動作確認する」だけで何を見るか書かれていない箇所はどれか
- **未確定事項の扱い**: 決まっていない箇所が「未定」と明示されているか。決まっていないまま断定形で書かれた箇所はどれか

## スコープ外

「今回の目的に不要だから削るべき」という理由だけの指摘（将来向け基盤整備、関係のない既存コード整理、YAGNI）はこのレビューの対象外とする。実行自体に矛盾しない将来向けステップは指摘しない。

ただし、以下のような scope 定義の矛盾によって計画が成立しない問題は引き続き対象とする。

- 後続 step に必要な作業が scope から漏れていて計画が実行不能
- 計画外の resource を変更しないと step が成立しない
- rollback 対象が計画の対象範囲に含まれていない

「不要だから scope 超過」は対象外だが、「scope 定義の矛盾によって計画が成立しない」は対象とする。

## Severity基準

| Severity | 扱い | 基準 |
|----------|------|------|
| **CRITICAL** | 必ず直す | ロールバック不可能な破壊的操作を含み、失敗時に取り返しがつかない |
| **HIGH** | 必ず直す | 依存関係の矛盾や検証手段の欠如により、計画が途中で破綻しうる |
| **MEDIUM** | 検討する | 手順の粒度が粗い、想定外ケースの考慮が薄い |
| **LOW** | 報告しない | 表現や順序の好みなど、実行可否に影響しない指摘 |

# 設計レビュー基準

レビュー範囲がアーキテクチャ文書や設計判断のときに使う。

指摘には行番号ではなく、対象箇所の見出しか原文の引用を添える。

## 観点

- **代替案の検討**: 他のアプローチが挙がっているか。挙がっている場合、却下理由が書かれているか。比較軸（性能・運用コスト・移行コストなど）が示されているか
- **スケール前提**: 想定するデータ量・リクエスト数・同時実行数が数値で書かれているか。その数値で破綻する箇所はどこか
- **障害モード**: 依存先が落ちたとき、タイムアウトしたとき、一部だけ成功したときの挙動が書かれているか。リトライする場合、同じ処理が 2 回走っても結果が変わらないか
- **運用・移行パス**: 既存システムからの切り替え手順、切り戻し手順、移行中に新旧が同時に動く期間の扱いが書かれているか
- **可観測性**: 障害が起きたとき、どのログ・メトリクスを見れば原因に到達できるか書かれているか
- **技術選定のバージョン整合性**: 選定した言語/ランタイム/FW/ライブラリが EOL を迎えていないか、サポート期限が設計の想定寿命より短くないか。設計が前提にしている API が、選定バージョンに存在するか。`references/deepwiki.md` の手順で確認した結果を根拠にする。**EOL しているという事実だけで自動的に HIGH にしない**。設計の想定寿命、運用開始時期、security support の有無、upgrade path の有無を見て判断する
- **必要以上の複雑さ**: 現在の要件・想定規模に対して、構成要素・レイヤー・サービス分割・拡張ポイント・メッセージング・キャッシュ・分散処理・運用機構が過剰になっていないか。より単純な設計で同じ要件を満たせる場合、複雑さを追加する具体的な根拠が書かれているか確認する。「スケール前提」の観点と突き合わせ、想定データ量・リクエスト数・同時実行数など具体的な数値から必要性を判断する。「将来スケールするかもしれない」のような抽象的な可能性だけでは根拠として認めない

## Severity基準

| Severity | 扱い | 基準 |
|----------|------|------|
| **CRITICAL** | 必ず直す | 障害時にデータ損失やサービス停止を招く設計上の欠陥 |
| **HIGH** | 必ず直す | 想定負荷で破綻する設計、移行パスの欠如、代替案検討なしで明らかに劣る選択 |
| **MEDIUM** | 検討する | 運用性・監視の考慮不足 |
| **LOW** | 報告しない | 好みの範囲の指摘 |

**必要以上の複雑さの Severity は固定しない。** 過剰設計そのものではなく、それによって実際に増える影響——構成要素間の障害伝播範囲、移行・運用コスト、変更のたびに触る箇所の数——を基準に上の表へ当てはめる。障害モードや可観測性を悪化させる過剰な構成要素は HIGH、単に運用の手間が増えるだけなら MEDIUM に収める。想定規模に対して明らかに過剰な指摘 1、2 件に絞り、些細な設計選好を積み上げない。

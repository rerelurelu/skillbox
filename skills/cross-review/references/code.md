# コードレビュー基準

レビュー範囲がソースコードのときに使う。種別を判定できないときの既定値でもある。

## 観点

観点は役割別のレビュアー定義に書いてある。このファイルはレビュー種別ごとの Severity 基準を持つ。

## スコープ外

不要な実装・抽象化・汎用化・将来向け拡張など、「現在の挙動は正しいが、より単純にできる」という理由だけの指摘はこのレビューの対象外とする（`lean-review` スキルの担当範囲である）。interface が 1 実装しかない、factory が不要、helper を inline できる、といった指摘は報告しない。

**責務の配置・依存の向き・重複実装・保守運用上の問題は、このレビューの対象に含める。** ただし、変更時・運用時・障害時に成立する具体的な誤りを evidence に書けるものに限る。「なんとなく汚い」「将来困るかもしれない」で終わる指摘は報告しない（例: factory の分岐により `type=B` で誤った実装が選ばれる、は対象。factory の分岐が多いこと自体は対象外）。

線引きは 1 文で書ける。`lean-review` が扱うのは消せるコードであり、`cross-review` が扱うのは置き場所が違うコードである。

## Severity基準

| Severity | 扱い | 基準 |
|----------|------|------|
| **CRITICAL** | 必ず直す | バグ、セキュリティ脆弱性、データ損失、クラッシュ |
| **HIGH** | 必ず直す | 設計上の欠陥、レースコンディション、重大なロジックエラー、同一の業務ルールが複数箇所に重複しており片方だけ更新されるとデータまたは表示が食い違う |
| **MEDIUM** | 検討する | パフォーマンス、変更時に複数箇所の同時修正を要する構造、可観測性の不足、軽微なロジックの抜け |
| **LOW** | 報告しない | スタイルの好み、軽微な指摘、見た目上の指摘 |

**非推奨/廃止予定 API の使用は、ラベルではなく確認結果で Severity を決める。** `references/deepwiki.md` の手順で確認したうえで、以下に当てはめる。

| Severity | 確認結果 |
|----------|---------|
| HIGH | 使用中のバージョンで既に重大な誤動作を起こす／security fix の対象外になっている／計画上避けられない近い upgrade で削除される／実際の互換性破壊が確認できる |
| MEDIUM | deprecated/discouraged だが使用中のバージョンでは正常に動作し、即時の障害や互換性破壊は無い。将来の移行負債として妥当な指摘 |
| 報告しない | 「別の書き方が今は推奨」というだけで、現在の実装に実害も移行リスクも無い |

deepwiki で確認できなかった場合は「未検証」として Severity を 1 段下げる（`references/deepwiki.md` 手順 4）。

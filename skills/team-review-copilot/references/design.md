# Design Review Criteria

Use these criteria when the reviewed scope is an architecture document or design decision.

指摘には行番号ではなく、対象箇所の見出しか原文の引用を添える。

## 観点

- **代替案の検討**: 他のアプローチが挙がっているか。挙がっている場合、却下理由が書かれているか。比較軸（性能・運用コスト・移行コストなど）が示されているか
- **スケール前提**: 想定するデータ量・リクエスト数・同時実行数が数値で書かれているか。その数値で破綻する箇所はどこか
- **障害モード**: 依存先が落ちたとき、タイムアウトしたとき、一部だけ成功したときの挙動が書かれているか。リトライする場合、同じ処理が 2 回走っても結果が変わらないか
- **運用・移行パス**: 既存システムからの切り替え手順、切り戻し手順、移行中に新旧が同時に動く期間の扱いが書かれているか
- **可観測性**: 障害が起きたとき、どのログ・メトリクスを見れば原因に到達できるか書かれているか
- **技術選定のバージョン整合性**: 選定した言語/ランタイム/FW/ライブラリが EOL を迎えていないか、サポート期限が設計の想定寿命より短くないか。設計が前提にしている API が、選定バージョンに存在するか。ブリーフィングに含まれる調査結果を基準に判断する

## Severity基準

| Severity | Action | 基準 |
|----------|--------|------|
| **CRITICAL** | Must fix | 障害時にデータ損失やサービス停止を招く設計上の欠陥 |
| **HIGH** | Must fix | 想定負荷で破綻する設計、移行パスの欠如、代替案検討なしで明らかに劣る選択 |
| **MEDIUM** | Consider | 運用性・監視の考慮不足 |
| **LOW** | Skip | 好みの範囲の指摘 |

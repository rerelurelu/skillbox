# Backend Domain Criteria

Additive criteria for scope containing backend/server code (APIs, business logic, data access). Use alongside the type criteria (`references/<type>.md`), not in place of them.

## 観点

- **クエリ性能**: ループの中でクエリを発行している箇所がないか（N+1）。`WHERE` / `ORDER BY` に使う列にインデックスがあるか。件数の上限を指定せずに全件取得している箇所がないか
- **トランザクション境界**: 2 つ以上のテーブル・レコードを更新する操作が 1 つのトランザクションに入っているか。入っていない場合、片方だけ成功したときにどのデータが食い違うか。トランザクションの中で外部 API 呼び出しやファイル操作をしていないか
- **入力検証・認可**: リクエストの値が型・範囲・長さで検証されているか。「そのユーザーがそのリソースを操作してよいか」の確認が、ハンドラごとに存在するか（認証だけで認可がない経路がないか）
- **エラーハンドリング・冪等性**: 同じリクエストが 2 回届いたとき、2 回目で何が起きるか（二重登録、二重課金、二重送信）。失敗時に既に書き込んだ分が残らないか
- **並行性**: 読み取ってから書き込むまでの間に、他のリクエストが同じレコードを更新できるか。複数のロックを取る順序が経路ごとに違わないか
- **リソース管理**: コネクション・ファイルハンドル・ストリームが、エラーで途中 return したときにも解放されるか

## Severityの当てはめ

type 側の Severity 表に当てはめる。判断が割れる観点は以下に寄せる。

| 観点 | 当てはめ先 |
|------|-----------|
| 認可漏れ、入力検証の欠如による不正操作 | CRITICAL（セキュリティ脆弱性） |
| トランザクション境界の誤りによるデータ不整合 | CRITICAL（データ損失） |
| 冪等性の欠如（二重登録・二重課金） | CRITICAL（データ損失） |
| レースコンディション、ロック順序の不一致 | HIGH |
| リソースリーク | HIGH（稼働時間に比例して枯渇するため） |
| N+1、インデックス不足、全件取得 | MEDIUM |

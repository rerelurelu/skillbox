# コードレビュー基準

レビュー範囲がソースコードのときに使う。種別を判定できないときの既定値でもある。

## 観点

どこを見るかを列挙する。見つけたものの扱いは下の Severity 基準で決める。

- **境界値と異常系**: 空文字・空配列・null・0 件・上限超過・負値を渡したとき何が返るか。`length` や添字アクセスの前に存在確認があるか
- **エラー処理の経路**: 失敗が握り潰されていないか（空の catch、無視される戻り値）。リトライする処理が同じ入力で 2 回実行されても安全か
- **並行性**: 同じデータに複数の実行が同時に到達したとき、読み取りと書き込みの間に他の実行が割り込めるか
- **状態とライフサイクル**: 初期化前・解放後のアクセス、途中で return したときのリソース解放漏れ
- **信頼できない入力の流れ**: 外部から来た値がクエリ・シェルコマンド・HTML・ファイルパスに、変換を挟まずに到達していないか
- **バージョン整合性**: 使用中の言語/ランタイム/フレームワーク/ライブラリのバージョンに対して、非推奨(deprecated)または将来廃止予定の API を使っていないか。そのバージョンで推奨される書き方に沿っているか。ロックファイルで実際のバージョンを特定し、`references/deepwiki.md` の手順で確認した結果を根拠にする。**記憶だけを根拠に「非推奨」と断定しない**
- **変更の波及**: 変更した関数・型・スキーマの呼び出し側で、更新されていない箇所がないか
- **過剰な実装・抽象化**: 今回の要件に無い将来の拡張のために、抽象化・インターフェース・factory/strategy/registry 等の仕組み・設定項目・汎用化・レイヤー・分岐・helper・未使用の将来向け機能が追加されていないか。より単純な実装で今回の要件を満たせる場合、複雑さを追加している理由がコード・コミットメッセージ・関連する計画のどこかに書かれているか。理由が見つからず、かつ今回の要件だけなら不要な複雑さは指摘する。以下は対象外とする: 既存のプロジェクト設計・規約に従うために必要なもの、既に複数箇所で必要になっている共通化、今回の要件から直接必要になる拡張性、不具合・セキュリティ・データ整合性を守るために必要な構造。「抽象化されている」という事実だけを理由にしない

## Severity基準

| Severity | 扱い | 基準 |
|----------|------|------|
| **CRITICAL** | 必ず直す | バグ、セキュリティ脆弱性、データ損失、クラッシュ |
| **HIGH** | 必ず直す | 設計上の欠陥、レースコンディション、重大なロジックエラー |
| **MEDIUM** | 検討する | パフォーマンス、保守性、軽微なロジックの抜け |
| **LOW** | 報告しない | スタイルの好み、軽微な指摘、見た目上の指摘 |

**非推奨/廃止予定 API の使用は、ラベルではなく確認結果で Severity を決める。** `references/deepwiki.md` の手順で確認したうえで、以下に当てはめる。

| Severity | 確認結果 |
|----------|---------|
| HIGH | 使用中のバージョンで既に重大な誤動作を起こす／security fix の対象外になっている／計画上避けられない近い upgrade で削除される／実際の互換性破壊が確認できる |
| MEDIUM | deprecated/discouraged だが使用中のバージョンでは正常に動作し、即時の障害や互換性破壊は無い。将来の移行負債として妥当な指摘 |
| 報告しない | 「別の書き方が今は推奨」というだけで、現在の実装に実害も移行リスクも無い |

deepwiki で確認できなかった場合は「未検証」として Severity を 1 段下げる（`references/deepwiki.md` 手順 4）。

**過剰な実装・抽象化の Severity は固定しない。** 過剰設計そのものではなく、それによって実際に増える影響——変更範囲、障害リスク、保守コスト、認知負荷、今後の変更の難しさ——を基準に上の表へ当てはめる。1 ファイル内で完結する小さな不要抽象化は MEDIUM 止まりが多い。呼び出し側を横断して波及する、または不要な設定項目が誤設定によるバグを生みうる場合は HIGH まで上がる。軽微な不要抽象化を大量に列挙しない。1 箇所で最も影響の大きいものに絞る。

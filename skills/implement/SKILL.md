# Implement

`$ARGUMENTS` に書かれた内容を実装し、レビューと仕上げの工程をすべて終えてから完了報告を出す。

各工程のスキルは、単独で呼ばれたときは結果を報告してユーザーに判断を返す作りになっている。このスキルから呼ぶときは、各スキルが「報告して止まる」と定めている箇所でも止まらず、判断が要る項目を保留リストに記録して次の工程へ進む。ユーザーへの質問は、最後の完了報告で 1 回だけ行う。

## 止まってよい場面

次の 3 つに限る。それ以外では、ユーザーに質問せず最後の工程まで進む。

1. 開始前: `$ARGUMENTS` が空、または依頼の解釈が複数あり、どれを選ぶかで実装の範囲や挙動が変わる。この場合は実装に入る前に質問する。
2. Step 2 の検証（lint / typecheck / test）が失敗し、自分の変更の範囲で直せない。壊れた状態の上でレビューや整理をしても結果が使えないため、ここで止めて完了報告の形式で報告する。報告の見出しは「完了」ではなく「中断」にする。
3. 依頼の実現に、新しい依存の追加、スキーマの変更、公開 API の変更が必要だと分かった。依頼文でそれが求められている場合は止まらない。

## 手順

Copy this checklist and track progress:

```
Implement Progress:
- [ ] Step 1: 実装
- [ ] Step 2: self-check
- [ ] Step 3: codex-review
- [ ] Step 4: lean-review
- [ ] Step 5: final-cleanup
- [ ] Step 6: 設計文書の推敲（対象があるときだけ）
- [ ] Step 7: 完了報告
```

途中経過として、各工程を終えるたびに結果を 1〜3 行で書く。各スキルが定める詳しい報告形式は使わず、詳細は Step 7 にまとめる。

保留リストには、項目ごとに次を記録する。

- 出どころの工程（例: codex-review #2）
- 場所（`file:line`）
- 現在の挙動を具体的な入力と結果で書いたもの
- 選択肢と、それぞれを選んだときに変わる挙動

### Step 1: 実装

`$ARGUMENTS` の内容を実装する。依頼の範囲だけを変更し、無関係な整理はしない。

### Step 2: self-check

`self-check` スキルを実行する。対象範囲は指定せず、未コミットの変更すべてとする。

self-check が「設計判断になるので直さず止まる」とした項目は、保留リストに入れて次へ進む。検証が失敗し自分で直せない場合は、「止まってよい場面」の 2 に当たるので止まる。

### Step 3: codex-review

`codex-review` スキルを実行する。対象範囲は指定せず、未コミットの変更とする。

- ACCEPT で修正が一意に決まる指摘は、codex-review の手順どおり直す。
- ACCEPT で「要判断」とした指摘は、保留リストに入れる。
- REJECT と DEFER は、Step 7 の表に載せるだけにする。
- `codex review` の出力が空、またはコマンドが失敗した場合は、1 回だけ再実行する。2 回目も失敗したら「codex-review: 実行できなかった」と記録して次へ進む。main agent が代わりにレビューすることはしない。

### Step 4: lean-review

`lean-review` スキルを実行する。lean-review は指摘を報告するだけで、コードを変更しない。指摘への対応はこのスキルが行う。

指摘を 1 件ずつ次のように扱う。

- 削除または置き換えをしても挙動が変わらず、変更が指摘された箇所の中で済むものは適用する。
- 挙動が変わるもの、公開 API や複数ファイルの構成を変えるもの、Step 3 で ACCEPT して直した箇所を元に戻すものは、適用せず保留リストに入れる。

適用した指摘が 1 件以上あれば、プロジェクトにある lint / typecheck / 関連する test を実行する。失敗したら、その失敗の原因になった適用を取り消し、その指摘を保留リストに移す。

### Step 5: final-cleanup

`final-cleanup` スキルを実行する。対象範囲は指定せず、未コミットの変更とする。final-cleanup の中で `deslop-comments` も実行される。

final-cleanup が「作業を止めてユーザーに報告する」とした項目（削除の是非が判断できないコードなど）は、保留リストに入れて次へ進む。

### Step 6: 設計文書の推敲

未コミットの変更に、design doc、ADR、設計書、仕様書のどれかにあたる日本語の文書が含まれるときだけ行う。置き場所やファイル名では判断せず、文書の中身で判断する。README、CHANGELOG、コードコメントは対象にしない。該当する文書が無ければ、Step 7 にその旨を 1 行書いて飛ばす。

文書ごとに次の順で行う。

1. `writing-style-jp` スキルを読み、「設計書・ADR で追加で守ること」に沿って文書を直す。数値、上限、エラー時の挙動が書かれていない箇所に、値を推測して書き足さない。書き足す値が会話や依頼文から確定できない場合は、保留リストに入れる。
2. `yomiyasu` スキル（Codex では `yomiyasu:yomiyasu`）でその文書を推敲する。yomiyasu が最終稿を別の名前で保存した場合は、その内容で元の文書を置き換え、別名のファイルを消す。
3. yomiyasu の「書き手に確かめたい点」は、保留リストに入れる。
4. yomiyasu がこの実行で作ったファイルやフォルダ（`.yomiyasu/` の検査記録、`*.material.txt` など）のうち、実行前に無かったものを消す。最終的な差分には、推敲した文書の変更だけを残す。

`writing-style-jp` または `yomiyasu` が使えない場合は、「<スキル名>: unavailable」と記録し、使える方だけを実行する。代わりに自分の基準で推敲することはしない。

### Step 7: 完了報告

最後に 1 回だけ、次の形式で報告する。実行しなかった工程や、存在しない check の行は書かない。

```
## 実装完了

### 変更内容
- <何をどう変えたか。挙動の変化は具体的な入力と結果で書く>

### 工程の結果
| 工程 | 結果 |
|---|---|
| self-check | <直したもの / 問題なし> |
| codex-review | 指摘 N 件: 修正 a、要判断 b、却下 c、見送り d |
| lean-review | 指摘 N 件: 適用 a、保留 b |
| final-cleanup | <削除した dead code、直したコメント> |
| 設計文書の推敲 | <推敲した文書 / 対象なし> |

### codex-review の指摘
<codex-review の Phase 4 の表をそのまま載せる。指摘が 0 件なら省く>

### 検証
- lint: <結果>
- typecheck: <結果>
- test: <結果>

### 確認したいこと
1. <保留項目>（出どころ: <工程> / 場所: `file:line`）
   現在の挙動: <具体的な入力と結果>
   - A: <案> — <選んだときの挙動>
   - B: <案> — <選んだときの挙動>
```

保留リストが空なら「確認したいこと」の節は書かない。検証が 1 つでも失敗している場合は、見出しを「実装完了」にせず、どの check がどう失敗したかを書く。

## 完了報告のあと

ユーザーが「確認したいこと」に回答したら、回答に沿って該当箇所を直し、変更したファイルに関係する lint / typecheck / test を再実行して結果を報告する。Step 2 から全工程をやり直すのは、ユーザーが求めたときだけにする。

commit と push はしない。ユーザーが求めたときに行う。

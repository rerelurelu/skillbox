# Feature

新規実装、機能追加、機能修正の手順。メインは設計と判断と確認を持ち、本番のコードは書かない。変更が小さくても、どんな理由があっても自分では書かずに実装役に任せる。目的はレビューを分けることで、手間を減らすことではない。スキル名（arena など）が出てきたら、qstack の SKILL.md の「使うスキル」にあるパスの SKILL.md を読んで従う。

```
Feature Progress:
- [ ] 1. 認識合わせ
- [ ] 2. 設計
- [ ] 3. 実装
- [ ] 4. コメントのレビュー
- [ ] 5. 検証
- [ ] 6. 攻撃レビュー
- [ ] 7. 修正の回と再レビュー
- [ ] 8. コミットのまとめ直し、報告、後片付け
```

## 1. 認識合わせ

1. 依頼に関係するコードと、渡された仕様書やドキュメントを読む。影響する呼び出し元もたどる。
2. 最初の返信で次の 4 つを出す。
   - 目的: 1〜2 文
   - 完了条件: 合否が判定できる形。例「1 万件のフィクスチャで全件が出力される」。「使いやすくする」のような判定できない書き方はしない
   - 仮定した業務ルール: 調べても決まらなかったケースと、それをどう扱うか。外れたら困るものから並べる。探す観点は入力（空、上限、形式違い、重複）、状態（キャンセル済み、削除済みなど）、権限、途中の失敗、既存データ、同時実行
   - 変えない範囲: 今の挙動を保つもの
3. 依頼文に「コードはまだ変えないで」があれば、ここで止まる。ユーザーが仮定を直したら、それを反映して工程 2 から進める。
4. 無ければ止まらずに設計へ進む。

## 2. 設計

1. データの形（型、状態、テーブル）を先に決める。
2. 形が 2 通り以上考えられるときは、2 案を並べて次の基準で選ぶ。選んだ理由と却下した案を記録する。
   - 1 つの状態に持ち主が 1 つ
   - 1 つの作業にやり方が 1 つ
   - 呼び出す側が知るべきことが一番少ない
   - no-overengineering の観点のうち、「設計でも使う」の列が「使う」のものに当たらない
3. 設計が大きい、または割れるときは、arena を種類「設計」で回す。大きいとは、新しいモジュールや公開インターフェースを作る、複数のモジュールの境界を変える、のどちらか。割れるとは、2 案の基準の評価が分かれて決められない状態。
4. 測れば決まる分岐（性能、ライブラリでできるかどうか）は、`${TMPDIR}` に使い捨てのコードを書いて測る。本番のソースには入れない。
5. 新しいデータ構造を作る、またはモジュールをまたぐ変更なら、設計を見せて止まる。それ以外は止まらずに実装へ進む。

## 3. 実装

1. 実装の形が何通りも考えられるとき（エラー処理の方式、抽象化の層、テストの構成が割れる）は、Sol に任せずに arena を種類「実装」で回す。結果が作業ツリーに反映されたら、意味のある単位でコミットして工程 4 へ進む。
2. `sol` のペインを用意する（herdr-panes、作業フォルダはリポジトリの作業ツリー）。
3. Sol に次の依頼文を送る。

```
次の内容を実装してください。スキルは使わずに作業してください。git の状態を変えるコマンド（commit、stash、checkout、reset、branch、rebase）は使わないでください。

## 認識合わせ
<目的、完了条件、変えない範囲、仮定した業務ルール>

## 設計
<決めたデータの形、触るファイル、選んだ案>

## 作業フォルダ
<絶対パス>

## 書くときの規則
- 作りすぎの基準: <no-overengineering の SKILL.md の絶対パス> を読み、表の観点のどれにも当たらないように書く。「当てはめないもの」に当たるものは消さない
- コメントとドキュメントは <technical-writing の SKILL.md の絶対パス> に従い、仕上げに <unslop の SKILL.md の絶対パス> を当てる
- 終える前に、変更全体を no-overengineering に照らして見直し、当たるものを直す。変えた関数名、型名、設定キー、コマンド名をリポジトリ全体で検索し、古いままのコメントとドキュメントも直す
- プロジェクトにある lint、typecheck、関連するテストを実行する。実行方法は package.json、build.gradle、Makefile などの実行定義、AGENTS.md、README の順に探す

## 報告
=== RESULT === の行から書き始め、=== END === の行で終えてください。
- 変更したファイルと内容
- 実行した lint、typecheck、テストのコマンドと結果
- 決めたこと: 設計に書いていないことで自分が決めたことと、その理由
- 却下した案: 検討してやめた案と、やめた理由
- コミットの単位: 変更を意味のある単位に分けたもの。単位ごとに、目的（1 行）と、含むファイルのパス
```

4. 完了を待って結果を読む。結果の「決めたこと」と「却下した案」を記録しておく（修正の回で使う）。
5. 報告の「コミットの単位」に沿ってコミットする（SKILL.md の「git」）。

## 4. コメントのレビュー

1. no-comments を範囲 `<開始時のコミット>..HEAD` で回す。直すのは Sol。
2. 変えない範囲に当たるので直さない `OVERRULED` は、報告の「確認したいこと」に入れる。
3. 受け入れた `OVERRULED` の直し方を決める。直し方が 1 つに決まるなら、メインは直し方を書かずに Sol に任せる。何通りも考えられて割れるなら、工程 3 の手順 1 と同じく arena を種類「実装」で回し、その `OVERRULED` は Sol に送らない。
4. 残った指摘があれば、Sol のペインの会話を消してから依頼する。依頼文は工程 3 の依頼文の「書くときの規則」と「報告」を含め、作業内容を「次のコメントを消す。`OVERRULED` の箇所は理由を読み、コメントが要らなくなるようにコードを直す。どう直したかは報告の『決めたこと』に書く」にする。
5. 完了を待ち、報告の「コミットの単位」に沿ってコミットする。

## 5. 検証

1. Agent ツールで `subagent_type: "relubox:verifier"`、`run_in_background: true` の subagent を起動し、認識合わせ、作業フォルダの絶対パス、差分の範囲 `<開始時のコミット>..HEAD` を渡す。実装の経緯は渡さない。
2. 結果の証拠を読む。判定と出力が合っていなければ、その完了条件を自分で確かめ直す。
3. 認識合わせで合意していない依存の追加があれば、報告の「確認したいこと」に入れる。
4. NOT VERIFIED があれば、工程 7 の修正の回に進む。INCONCLUSIVE は合格として扱わず、理由を報告に書く。
5. すべて VERIFIED か INCONCLUSIVE なら工程 6 へ進む。

## 6. 攻撃レビュー

1. interrogate を範囲 `<開始時のコミット>..HEAD`、run は開始時のコミットの先頭 7 文字で回す。
2. 仮定した業務ルールに関わる指摘は直さずに報告の「確認したいこと」に入れる。捨てた指摘の件数と理由は報告の「工程の結果」に入れる。
3. 確かめた指摘があれば工程 7 へ進む。無ければ工程 8 へ進む。

## 7. 修正の回と再レビュー

1. Sol のペインの会話を消して次をまとめて依頼する。依頼文は工程 3 の依頼文に、次の節を足したもの。
   - 最初の依頼の内容（認識合わせと設計）
   - そのあとにユーザーや工程から出た指示
   - 直すもの: 確かめた指摘（コマンド、出力、意図が求める出力）、または NOT VERIFIED の完了条件と検証の出力
   - 前回の Sol の報告の「決めたこと」と「却下した案」
2. 完了を待ち、報告の「コミットの単位」に沿ってコミットする。既存の単位を直した変更はその単位のコミットへの fixup コミットにする（SKILL.md の「git」）。
3. 工程 4 のコメントのレビューと工程 5 の検証をやり直す。
4. 攻撃レビューの指摘を直した回なら、修正の大きさで再レビューを決める。
   - 小さい（直した場所が指摘された関数の中だけで、新しい関数、ファイル、引数の変更が無い）: 指摘のコマンドを最新のコミットで実行し直し、失敗が消えたことを確かめる
   - 大きい（上を超えた）: 工程 6 の攻撃レビューをやり直す
5. エスカレーション: 同じ依頼で工程 5 の検証が 2 回続けて NOT VERIFIED になったら、`astra-fix` のペインに手順 1 と同じ依頼文を送る。報告の「工程の結果」に、エスカレーションしたことと理由を書く。`astra-fix` でも 2 回続けて NOT VERIFIED なら、報告を「中断」にして止まる。

## 8. コミットのまとめ直し、報告、後片付け

1. SKILL.md の「git」に従ってコミットをまとめ直す。
2. SKILL.md の「報告」の形で報告する。
3. 今回の作業で開いたペインを閉じ（herdr-panes の「後片付け」）、interrogate の worktree を `git worktree remove --force` で消す。

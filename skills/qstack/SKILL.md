# qstack

依頼内容は `$ARGUMENTS` とする。このファイルは全 playbook に共通する決まりを書く。工程の手順は playbook に書く。

このフォルダには次のファイルがある。

- [playbooks/feature.md](playbooks/feature.md): 新規実装、機能追加、機能修正の playbook

## 使うスキル

playbook の中でスキル名が出てきたら、次の SKILL.md を読んで従う。パスはこのファイルのフォルダから見た位置。依頼文に書くときは絶対パスにする。

| スキル | パス | 使う場面 |
|---|---|---|
| herdr-panes | `../herdr-panes/SKILL.md` | ペインを開く、依頼する、待つ、読む、閉じる |
| arena | `../arena/SKILL.md` | 設計が大きいか割れるとき、実装の形が割れるとき |
| no-comments | `../no-comments/SKILL.md` | 実装と修正の回のあと |
| interrogate | `../interrogate/SKILL.md` | 検証のあと |
| no-overbuild | `../no-overbuild/SKILL.md` | 実装役が書くときの規則、設計の基準 |
| writing-style-jp | `../writing-style-jp/SKILL.md` | コメント、ドキュメント、コミットメッセージ、報告の文章 |

subagent の定義はプラグインの `agents/` にある。検証役は `relubox:verifier`、コメントのレビュー役は `relubox:comment-reviewer`（no-comments が起動する）。

## 始める前の確認

1. 依頼の種類を決めて、playbook を選ぶ。

   | 依頼 | playbook |
   |---|---|
   | 新規実装、機能追加、機能修正 | [playbooks/feature.md](playbooks/feature.md) |

   どれにも当たらない（バグ修正、調査だけ、文書だけの変更）なら、qstack の対象外だと伝えて止まる。

2. 実行環境を確かめる。どれかを満たさなければ、足りないものを伝えて止まる。
   - `test -n "${HC_TERMINAL_SOCKET:-}"` が成功する（Herdr のアプリの中で動いている）
   - `codex` と `agy` のコマンドがある
   - git の作業ツリーに未コミットの変更が無い

3. 今いるブランチを確かめる。`main`、`master`、`develop` のどれかなら、作業ブランチを切ってから呼ぶように伝えて止まる。リポジトリの `CLAUDE.md` や `AGENTS.md` で直接コミットが認められている場合は続ける。

4. `git rev-parse HEAD` の値を「開始時のコミット」として記録する。

5. playbook の手順を todo リストに写して、上から進める。

メインの effort は high を前提にする。Claude Code の effort が high 未満なら、最初の返信で 1 行だけ伝えて、そのまま進める。

## 止まる場面

次のときだけ止まってユーザーの返事を待つ。それ以外は止まらずに最後まで進める。

- 依頼文に「コードはまだ変えないで」が含まれていて、認識合わせを出したとき
- 設計で新しいデータ構造を作る、またはモジュールをまたぐ変更になると決まったとき（設計を見せて止まる）
- 実装の途中で、認識合わせで合意した前提と矛盾する事実が分かったとき
- 元に戻せない操作が要るとき（deploy、本番データへの書き込み、データの削除、push、共有ブランチへの force-push、外部への連絡）
- 「始める前の確認」を満たさないとき

## 役割とモデル

| 役割 | モデル | effort | 動かし方 |
|---|---|---|---|
| メイン（認識合わせ、設計、arena のまとめ役、指摘の再現、コミット、報告） | Opus 5.5 | high | このセッション |
| 実装役 | Codex `gpt-6.2-sol` | high | ペイン `sol` |
| 実装のエスカレーション先 | Codex `gpt-6.2-astra` | high | ペイン `astra-fix` |
| 検証役 | Opus 5.5 | medium | subagent `relubox:verifier` |
| arena、コメントのレビュー、攻撃レビュー | 各スキルに書いてある | 各スキルに書いてある | 各スキルに書いてある |

ペインは herdr-panes に従って開く。run には開始時のコミットの先頭 7 文字を使う。`sol` と `astra-fix` は Codex（書き込みあり）の起動コマンドで、作業フォルダはリポジトリの作業ツリー。

subagent は `run_in_background: true` で起動し、毎回新しく起動する。前の subagent を再開しない。

## 依頼文に必ず入れること

ペインと subagent への依頼文には次を入れる。

- 認識合わせの内容（目的、完了条件、変えない範囲、仮定した業務ルール）
- 作業するフォルダの絶対パス
- 「スキルは使わずに作業する」
- 「結果は `=== RESULT ===` の行から書き始め、`=== END ===` の行で終える」（ペインの場合。herdr-panes の「依頼、完了の待ち方、結果の読み方」）
- 「結果は最後の返答にすべて書く。メッセージでは送らない」（subagent の場合）
- 文章を書く役割には `writing-style-jp` の SKILL.md の絶対パスと「コメントとドキュメントはこの規則で書く」
- 「git の状態を変えるコマンド（commit、stash、checkout、reset、branch、rebase）は使わない」。worktree は stash やブランチをほかの作業ツリーと共有するため、どの役割にも入れる

スキルの絶対パスはこのファイルのパスから求めて、依頼文に書く。

## git

- コミットするのはメインだけ。実装役が仕事を終えるたびに（実装、コメントのレビューの適用、修正の回、エスカレーション先の修正）、実装役の報告の「コミットの単位」に沿ってコミットする。コミットの数は増えてもよい。
  - 単位ごとに、ファイルをパスで指定して入れる（`git add <path>`）。`git add -A` と `git add .` は使わない
  - メッセージはそのリポジトリの書き方に合わせ、`writing-style-jp` に従う。最後のまとめ直しでそのまま残すため、作業用の仮のメッセージにしない
  - 修正の回で、既存の単位を直した変更は `git commit --fixup=<その単位のコミット>` にする。新しい単位の変更は普通にコミットする
  - コミットのあとに `git status --short` を見る。どのコミットにも入らなかったファイルが残っていたら、中身を見て決める。qstack の変更の一部ならコミットに入れる。実行でできた生成物（`__pycache__`、ビルドの出力など）なら入れずに、報告の「工程の結果」に書く
- arena と interrogate が使う worktree は、それぞれのスキルが作る。qstack は報告のあとに interrogate の worktree を消す。
- 報告の前に、開始時のコミットより後のコミットだけをまとめ直す。`GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <開始時のコミット>` で、fixup コミットを元の単位のコミットに畳む。畳んだあとの各コミットが単独で成り立つ（そのコミットの時点でテストが通る）ことを確かめる。成り立たないコミットがあれば、前後のコミットとまとめる。
- 開始時のコミットより前のコミットには触らない。push しない。

## 報告

最後に 1 回だけ、次の順で書く。実行しなかった工程の行と、空の節は書かない。

```
## 実装完了（検証が 1 つでも VERIFIED でなければ「中断」）
目的: <認識合わせの目的>
開始時のコミット: <hash>（`git reset --soft <hash>` で qstack の変更を未コミットに戻せる）

### 変更内容
- <何をどう変えたか。挙動の変化は具体的な入力と結果で書く>

### 完了条件
| 完了条件 | 判定 | 証拠 |
|---|---|---|
| <条件> | VERIFIED / NOT VERIFIED / INCONCLUSIVE | <実行したコマンドと出力の要点> |

### 仮定した業務ルール（外れたら困る順）
1. <仮定> — <どう実装したか>

### 決めたこと
- <決めたこと> — <理由>（却下した案: <案> — <理由>）
- <arena を回した場合: 元にした候補、移植したもの、審査役とメインの採点>

### 工程の結果
| 工程 | 結果 |
|---|---|
| 設計 | arena あり／なし |
| 実装 | 修正の回 N 回、エスカレーションあり／なし |
| コメントのレビュー | 指摘 N 件: 適用 a |
| 検証 | 完了条件 N 件中 VERIFIED a |
| 攻撃レビュー | 指摘 N 件: 再現できた a、捨てた b（攻撃役ごとの捨てた件数と理由） |
| コミット | <まとめ直した後のコミット一覧> |

### 確認したいこと
1. <項目>（出どころ: <工程> / 場所: `file:line`）
   今の挙動: <具体的な入力と結果>
   - A: <案> — <選んだときの挙動>
   - B: <案> — <選んだときの挙動>
```

証拠の欄にはコマンドと出力の要点だけを書く。出力の全文はユーザーに求められたら出す。報告の文章は `writing-style-jp` に従う。

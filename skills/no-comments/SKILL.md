# No comments

## 観点

番号は no-overengineering の観点と共通の固定の ID で、付け方は no-overengineering の SKILL.md（このファイルのフォルダから見て `../no-overengineering/SKILL.md`）の「観点」に従う。

| # | 観点 | 当たると言える根拠 |
|---|---|---|
| 12 | コードの動きをなぞるだけのコメント、コメントアウトされたコード | そのコメントとコード |
| 13 | 自分たちのコードの分かりにくさを補うコメント、名前を良くすれば要らなくなる説明 | コメントが補っている内容と、それがコード（名前、関数の分け方、型、設計）で表せること |
| 14 | 変更の外にあるコメントやドキュメントが、変更前の内容のまま残っている | 変えた名前や挙動の検索結果と、古い記述の場所 |
| 17 | 正しさ、バグ、安全性を捕まえる lint や型チェックのルールを抑制している（`eslint-disable`、`@ts-ignore`、`@ts-expect-error` など） | 抑制しているルールの名前と、そのルールが防ぐ誤り |
| 18 | 同じ説明が複数のコメントやドキュメントに書いてある | 同じ説明が書いてある場所すべて |
| 19 | コメントが説明の代わりに別のファイルやクラスの場所を示している。またはシンボルの名前で示せるものを相対パスで示している | 示している場所と、示さなくても読めること、または代わりに書けるシンボルの名前 |
| 20 | コメントに、自分たちのチケット番号、PR の番号、作業の経緯を書いている | 書いてある番号や経緯 |
| 21 | コメントが消した仕様や挙動、前の書き方に触れている（「〜せず」「以前は〜だった」「〜は廃止した」） | 触れている箇所と、それが今のコードに無いこと |

## 当てはめないもの

次のコメントは観点に当たるように見えても消さない。

- 完了条件や依頼文で明示的に求められたもの
- コードで表せないことを書いたもの
  - 自分たちでは変えられない外部の事情（依存ライブラリ、プラットフォーム、ベンダー、プロトコル）と、その出典になる外部の issue や RFC へのリンク
  - 業務ルールや仕様の根拠（締め日の扱い、対象外にする条件、運用や法規上の制約）
  - 関数、クラス、型、モジュールの、名前では表せないこと（引数と戻り値の意味、呼ぶ側が守る条件、名前から読めない副作用）
  - ツールのための指示（ライセンスのヘッダー、`prettier-ignore` のようなフォーマッタの指示、観点 17 に当たらない lint や型チェックの抑制）

## 範囲

呼び出し元が差分の範囲を渡す。単独で呼ばれたときは `$ARGUMENTS` のコミットから HEAD まで。`$ARGUMENTS` が無ければ、`main` から分かれた地点から HEAD まで。

## 手順

1. Agent ツールで `subagent_type: "relubox:comment-arbiter"`、`run_in_background: true` の subagent を起動し、次を渡す。
   - 意図（目的、完了条件、変えない範囲、仮定した業務ルール）。単独で呼ばれて意図が無ければ、コミットメッセージから 1〜2 文で書く
   - 作業フォルダの絶対パス
   - 差分の範囲
   - このファイルの絶対パス
   - 前の回で捨てた指摘と理由。前の回が無ければ渡さない
2. 結果を点検する。次の指摘は捨てる。
   - 「当てはめないもの」に当たるコメントを消そうとしている
   - 差分の範囲の外を指している（観点 14 と、観点 18 で範囲の中と重なる場所として挙げたものを除く）
   - コメントとドキュメント以外の書き方を指摘している（`OVERRULED` を除く）
   - ドキュメントを観点 14、18 以外で指摘している
   - 観点 14 で挙げた記述が、すでに今の名前と挙動に合っている
   - `OVERRULED` に理由が書いていない
   - 前の回で捨てた指摘と同じ前提のまま挙げ直している

   `OVERRULED` を直すと変えない範囲を壊す（公開 API の名前を変えるなど）ものは、直さずに分けて返す。
3. 残った指摘を直す。`OVERRULED` は理由だけが書いてあるので、直し方は直す側が決める。
   - qstack から呼ばれたとき: 指摘の一覧を qstack に返す。直し方は qstack の playbook で決め、直すのは qstack の実装役
   - 単独で呼ばれたとき: 自分でコメントを消し、観点 14 の記述を書き直す。`OVERRULED` は理由を読んで直し方を決め、コメントが要らなくなるようにコードを直す。直し方が何通りも考えられて割れるときは、arena を種類「実装」で回す。直したら、プロジェクトの lint、typecheck、関連するテストを実行する

## 返答

- qstack から呼ばれたとき: 受け入れた指摘の一覧（消すコメント、書き直す記述、`OVERRULED` と理由）、変えない範囲に当たるので直さない `OVERRULED`、捨てた指摘と理由
- 単独で呼ばれたとき: 消したコメントの数、書き直した記述の数、`OVERRULED` ごとの直し方、実行した lint、typecheck、テストの結果、変えない範囲に当たるので直さなかった `OVERRULED`、捨てた指摘と理由
